More Vanilla with ActiveJob

Published 2026-06-30

ActiveJob is the framework's default API for orchestrating async work. It's built into ActionMailer and it's what every Rails application starts out with. ActiveJob comes with a Sidekiq adapter so that teams operating the job infrastructure have flexibility to choose how their jobs run.

As with most things Rails, ActiveJob is optimized for readability, and thus productivity. It moves boilerplate to where it belongs — the framework — using the same convention-over-configuration philosophy that Rails was originally sold on. Its declarative async orchestration API allows authors to write jobs with clear intent where business and orchestration logic is clearly separated.

Why it matters

  • Readability: Clearer, more natural wording lets the reader parse the code with less effort. A clean `perform` avoids inviting domain logic inclusions.
  • Intent: Why is this code here, and what is it actually doing? A declarative API lets us tell the two apart.
  • Focus: What is important and what is merely supporting? The load-bearing line should stand out, not drown in boilerplate.
  • Correctness: By delegating boilerplate to the framework, backoff math and retry counters come from battle-tested defaults.

Side-by-side

In this section we'll compare common practices and how they're expressed across the two APIs.

A job with no overrides
Sidekiq::Job
class User::MergeJob
  include Sidekiq::Job

  def perform(user_id, other_user_id)
    # ...
  end
end
ActiveJob
class User::MergeJob < ApplicationJob
  def perform(user, other_user)
    # ...
  end
end

Every Rails application gets generated with an ApplicationJob, a natural place for per-application overrides of framework defaults. Monkey patching Sidekiq::Job would be bad form, so we'd either have to invent a custom module or superclass to share application-wide behaviour.

A record deleted before perform
Sidekiq::Job
def perform(user_id, other_user_id)
  user       = User.find_by(id: user_id) or return
  other_user = User.find_by(id: other_user_id) or return

  user.merge other_user
end
ActiveJob
discard_on ActiveJob::DeserializationError

def perform(user, other_user)
  user.merge other_user
end

The concept of discarding the job when the records it operates on are gone is expressed declaratively with discard_on compared to two hand-written guard clauses.

Ideally jobs should only contain a single call back to the domain model, after all, their job is to orchestrate async workloads, not to know the domain. When the boilerplate is twice as long as the domain call, what's important drowns in boilerplating.

By separating the domain call from the async orchestration the two responsibilities of the job are clearly separated and the reader can efficiently read the lines that matter.

Discard on an exception
Sidekiq::Job
def perform(user_id, other_user_id)
  user = User.find(user_id)
  other_user = User.find(other_user_id)

  user.merge other_user
rescue SelfMergeError
  # swallowed — a silent discard
end
ActiveJob
discard_on SelfMergeError

def perform(user, other_user)
  user.merge other_user
end

discard_on also allows us to be declarative about expected exceptions. Same arguments here, what to re-run and what to discard stays declarative rather than mixed with the domain call.

In addition, discard_on fires a named discard.active_job event you can see in APM or assert in a spec, where a swallowed rescue leaves nothing to tell a deliberate discard from a no-op run.

Retry budget per error class
Sidekiq::Job
sidekiq_retry_in do |count, exception|
  if exception.is_a?(ActiveRecord::RecordInvalid) &&
    count >= MAX_ATTEMPTS - 1
    :discard
  end
end
ActiveJob
retry_on ActiveRecord::RecordInvalid, attempts: 3

Different retry budgets for different exceptions is a great way to ease up queue load without sacrificing reliability. retry_on makes this easy to reach for while Sidekiq's sidekiq_options retry: makes it something programmers would want to avoid unless absolutely necessary.

In practice this leads to less efficient retries and leaves more room for errors when repeated re-run logic has to be copy-pasted between jobs and is easy to misread. Matching the number silently shrinks the budget for transient infrastructure errors — deadlocks, timeouts.

Retry backoff per error class
Sidekiq::Job
sidekiq_retry_in do |count, exception|
  case exception
  when ThrottledError then 15 * (4**count) + rand(0..30)
  when TransientError then 5 * (count + 1)
  end
end
ActiveJob
retry_on ThrottledError, wait: :polynomially_longer, attempts: 8
retry_on TransientError, wait: 5.seconds, jitter: 0.3, attempts: 5

retry_on gives per-class attempt budgets, framework backoff (:polynomially_longer, or a wait: proc), and jitter — declaratively. The hand-rolled sidekiq_retry_in makes you own the branching and the backoff math. Reading :polynomially_longer immediately communicates what matters while the custom maths is significantly trickier to extract intent from.

The block format has one case where it can do more: when exception classes carry their own retry counts. I've never needed it, but it's the one case where I could see dropping down to Sidekiq::Job being warranted.

Arguments that survive a deploy
Sidekiq::Job
Job.perform_async(user.id, other_user.id)

def perform(user_id, other_user_id)
  user = User.find(user_id)
  other_user = User.find(other_user_id)

  user.merge other_user
end
ActiveJob
Job.perform_later(user:, other_user:)

def perform(user:, other_user:)
  user.merge other_user
end

GlobalID lets you pass records and keyword arguments directly. Add or reorder an argument and jobs already in the queue don't silently misbind mid-deploy the way positional ids do. Because it allows keyword arguments, there's also far less risk of passing arguments in the wrong order.

Uniqueness / de-duplication
Sidekiq::Job
sidekiq_options unique_for: 24.hours

def perform(user_id, other_user_id)
  user = User.find(user_id)
  other_user = User.find(other_user_id)

  user.merge other_user
rescue ActiveRecord::RecordNotUnique
  # unique_for isn't guaranteed, race still has to be handled with index.
end
ActiveJob
discard_on ActiveRecord::RecordNotUnique

def perform(user, other_user)
  user.merge other_user
end

Sidekiq Enterprise's unique_for drops a duplicate enqueue with a best-effort Redis lock keyed on a digest of the job's class, queue, and arguments. It's handy for pruning redundant work, but Sidekiq's own docs say not to rely on it for correctness. When uniqueness is a real invariant, the database — a unique index — is the exact, adapter-independent guarantee.

One test seam, not two
Sidekiq::Job
# inline! is thread-local, so jobs on the Puma
# thread (Playwright) miss it — reach for the global
config.around(:each, sidekiq: true) do |ex|
  prev = Sidekiq::Testing.__global_test_mode
  Sidekiq::Testing.inline!
  ex.run
ensure
  Sidekiq::Testing.__global_test_mode = prev
end

perform_enqueued_jobs do
  button("Merge").click
end
ActiveJob
# crosses the thread boundary out of the box
include ActiveJob::TestHelper

perform_enqueued_jobs do
  button("Merge").click
end

ActiveJob's test helpers run enqueued work inline no matter which thread executes it. Sidekiq's own inline mode is thread-local, so a job triggered through the Puma server thread in a feature or Playwright spec never sees it — the suite has to reach past the public API to Sidekiq::Testing.__global_test_mode to cross the boundary. A job written against perform_enqueued_jobs never needs that.

The same API as your mailers
Sidekiq::Job
# mailers enqueue through ActiveJob
UserMailer.welcome(user).deliver_later

# jobs use a different API
User::MergeJob.perform_async(user.id, other_user.id)
ActiveJob
# mailers enqueue through ActiveJob
UserMailer.welcome(user).deliver_later

# jobs use the same API
User::MergeJob.perform_later(user, other_user)

deliver_later is ActiveJob: every mail we send is already an ActionMailer::MailDeliveryJob on the Sidekiq adapter. So the question was never whether to run ActiveJob — it's whether the rest of our jobs share its API or speak a second one right beside it. An ActiveJob enqueues with perform_later and takes records, reading like the mailer on the line above; a Sidekiq::Job enqueues with perform_async and takes ids — a parallel-but-different surface to keep in your head.

And it isn't a small footprint: every mailer we have — dozens of deliver_later call sites, every one an implicit ActiveJob running in production today — instrumented, retried and queued exactly like the app jobs this proposes.

When to drop down to Sidekiq

A few things ActiveJob can't express, and they're reason enough to write those particular jobs as a plain Sidekiq::Job — no apology needed:

  • Batch completion callbacks. Sidekiq::Batch runs something once a whole fan-out finishes, with success/failure counts. ActiveJob has no equivalent.
  • Enqueue-level de-duplication. unique_for drops a redundant enqueue before it runs (best-effort — keep any real invariant in the database regardless). This can matter when thousands of jobs are expected to clash.
  • Retry routing. retry_queue: sends retries to a different queue than the first attempt — the one sidekiq_options setting in real use here with no ActiveJob equivalent.
  • Raw throughput. A trivial job body at very high volume or fan-out, where the adapter's per-job (de)serialization is a meaningful fraction of the work. Sidekiq claims a ~60-100% margin to ActiveJob when draining 500k no-op jobs.

What I'm not claiming / suggesting

  • Not "drop Sidekiq." It stays the engine.
  • Not "ActiveJob is faster." It isn't, and sometimes it can matter.
  • Not "re-write". Existing jobs stay; this is about the default for new ones.

Considered arguments for Sidekiq

The case against defaulting to ActiveJob is worth stating plainly. The strongest objections, and where we land on each:

  • "It's another layer to debug." It isn't a new one. config.active_job.queue_adapter = :sidekiq is already set application-wide, so every mailer and every existing ApplicationJob runs through the adapter in production today. Defaulting new jobs to it widens a path we already operate and instrument — it doesn't introduce one. If we're having real issues here, we should solve them with focused tooling that doesn't degrade application-level readability in every job.
  • Middleware compatibility. We tested it. Tenant context is carried by Sidekiq::CurrentAttributes, which sits beneath the adapter and travels in the job payload, not on the wrapper. A spec that enqueues under one tenant, makes a different tenant current, and then drives the job the way the Sidekiq processor does confirms the enqueuing tenant is the one restored — on the first attempt and again on a retry_on retry, never the ambient one. The concern is legitimate in principle; in practice the context rides below the layer that caused the scares, and the test is there to keep it that way. It has rough edges, but they are the ones a plain Sidekiq::Job has too.
  • Retry semantics don't line up one-to-one. ActiveJob counts attempts its own way — an executions counter rather than the retry_count our middleware injects, and a per-class attempts: budget rather than one global retry:. The names and numbers differ, but nothing is lost: a job that needs the attempt count reads executions, and retry_on / discard_on say declaratively what the hand-rolled branching used to. It's a different vocabulary for the same thing, learned once.
  • GlobalID adds a lookup per argument. Deserializing a record runs a query before perform begins — usually the same query the body would have run anyway. For a trivial body at high volume it's overhead, which is precisely the raw-throughput case we already keep on Sidekiq::Job. And when you need to control loading or handle a half-missing set of records, pass ids: ActiveJob takes them too — GlobalID is opt-in by passing the record.
  • Two idioms in one codebase. We already run both — dozens of ActiveJob jobs and every mailer beside hundreds of plain Sidekiq jobs. A stated default plus the table below lowers the per-job decision cost rather than adding to it, and nothing forces a rewrite of what already works. Dropping down to Sidekiq::Job will read as an explicit optimization decision.

Current is not a design surface

Tenant context survives the adapter, and it survives retries. That is worth knowing; it isn't worth designing on. Sidekiq::CurrentAttributes snapshots Current into the payload at enqueue and restores it around perform. The general case holds — the enqueuing tenant is what perform sees, on the first attempt and on every retry — and ambient worker state never leaks in: the Rails reloader blanks Current before the middleware chain opens, so a payload without a snapshot runs with no tenant rather than with somebody else's. The edges are narrow, but sharp:

  • A retry re-snapshots. retry_on re-enqueues from inside the restored scope, so a job that reassigns Current mid-work is retried as the tenant it switched to, not the one that enqueued it. Sidekiq's own retry re-pushes the original payload verbatim.
  • The restore is scoped to the middleware chain. Anything enqueued after it unwinds — a Sidekiq::Batch callback, a death handler, sidekiq_retries_exhausted — carries no tenant at all. That's why those call sites already thread company_id through by hand.
  • It rests on nesting order. The reloader has to wrap the middleware chain, and Load has to stay outermost inside it. Both hold today; neither is asserted anywhere except in that one spec.
  • Attributes can vanish silently. Load rescues the NoMethodError and drops attributes the class no longer responds to, so renaming one drops it from every in-flight payload without an error.
  • Everything on Current rides along. Not just the tenant: set disable_company_scope mid-job and raise, and the retry inherits it.

So the safer habit is the boring one: pass what the job needs and resolve the tenant from it. Candidate.find(id).company is a fact derived from the argument the job was handed; Current.company is ambient state restored by two middlewares and an executor hook. They usually agree. Only one of them is checkable at the call site, and only one still holds when the job is replayed from the dead set or invoked from a batch callback. Treat Current as scoping convenience and telemetry, not as the authority a job makes decisions on.

Our compatibility

Taking stock of every job we run today:

  • About an eighth are already ActiveJob — the ApplicationJob jobs plus every mailer.
  • More than half of the remaining Sidekiq jobs convert with no change at all.
  • A further chunk converts once a handful of low-volume unique_for jobs move to discard_on plus a DB index.
  • Rolled up: roughly three-quarters are ActiveJob today or could be; the remaining quarter genuinely stay on Sidekiq.

Additional benefits

Beyond the side-by-sides, a few things come for free with ActiveJob that are easy to overlook:

  • Locale & timezone carry over. A job formats dates and translates copy the same way the request that enqueued it did, instead of silently falling back to the default.
  • Lifecycle callbacks. Cross-cutting concerns live as around_perform / rescue_from declarations rather than hand-written Sidekiq middleware.
  • Custom argument serializers. Pass a domain type like any other argument once it's registered, instead of hand-packing it into a hash of primitives at every call site.
  • One scheduling API. set(wait:, wait_until:, queue:, priority:) is the same fluent surface across every job — and the one the mailers already use.
  • Less Sidekiq & commercial-license lock-in. Jobs are written against the framework, not the adapter, so the backend stays a config choice rather than a rewrite. And the Sidekiq-only features that keep a job on Sidekiq — Batch, unique_for, super_fetch, rate limiting — are paid Pro/Enterprise add-ons; every plain ActiveJob is one that doesn't reach for them, keeping the commercial lock-in surface small.

The concrete proposal

Default to ActiveJob for ordinary work. Reach for Sidekiq::Job when we truly need the raw performance for massive amounts of trivial jobs.

What we win is jobs that read as intent with less room for errors, arguments that survive a deploy, observable discards, and built-in test compatibility — on the default framework Rails already runs our mail through. Sidekiq stays the engine; ActiveJob just makes the ordinary job a more legible default.
