Default to ActiveJob

Sidekiq stays the engine. ActiveJob becomes the authoring API — and the default for ordinary jobs.

← →

Where this comes from

A competency-merge PR added an ApplicationJob. The platform team pushed back: the codebase convention is native Sidekiq::Job, and they're right that most of app/jobs is exactly that.

That conversation settled a single job. This deck is the broader question it raised, brought to where it belongs — a proposal, not a PR exception:

Should ActiveJob be our default way to write a background job?

I want to be upfront: this is a continuation of a code review thread, and I lost the local battle on purpose — one PR isn't the place to set a team-wide convention. So I'm bringing the actual question here instead.

The platform team's review was sharp and a lot of it landed. I'll be honest about which parts.

← →

The proposal

ActiveJob is an API, not an engine

ActiveJob doesn't replace Sidekiq — it runs on Sidekiq. The choice isn't "ActiveJob or Sidekiq." It's which authoring surface we reach for first.

Default to ActiveJob for ordinary jobs. Drop to native Sidekiq::Job when you need something only Sidekiq offers. Today that default is inverted.

This is the single most important framing and the one that keeps the discussion honest.

Nobody is proposing we remove Sidekiq. Sidekiq Enterprise, super_fetch, the reliable scheduler — all of that stays. The Sidekiq adapter is what executes ActiveJob. So the real question is narrow: when a developer sits down to write a job, what's the default shape of the file?

← →

Today the default is "roll your own"

New native jobs repeat the same hand-written plumbing: id arguments, find_by(id:) guards, explicit rescue blocks, a single global retry: number, and manual Current wiring.

the shape every native job re-derives 
class SomeJob
  include Sidekiq::Job
  sidekiq_options queue: :default, retry: 3

  def perform(some_id, other_id)
    some = SomeRecord.find_by(id: some_id) or return
    other = OtherRecord.find_by(id: other_id) or return
    Current.company = some.company
    # ...the two lines of actual work...
  rescue SomeProgrammerError
    # discard
  end
end

None of the boilerplate is logic. It's a re-implementation of things the framework already does.

This is descriptive, not a dig. The pattern works. The point is just that each new job hand-rolls the same scaffolding, and the actual intent — the two lines of work — gets buried in the middle.

← →

The error contract reads at the top

ActiveJob — policy as configuration

class Merge::Job < ApplicationJob
  discard_on ActiveRecord::RecordNotFound
  discard_on SelfMergeError
  retry_on ActiveRecord::RecordInvalid, attempts: 3

  def perform(target:, absorbing_ids:, user:)
    target.merge absorbing_ids:, user:
  end
end

Read the whole failure policy without reading a line of business logic.

Native — policy spread through the body

def perform(target_id, absorbing_ids, user_id)
  target = ScorecardCriterium.find_by(id: target_id) or return
  user = User.find_by(id: user_id) or return
  Current.company = target.company
  target.merge absorbing: scope(absorbing_ids), user:
rescue SelfMergeError
  # discard
end
# ...plus sidekiq_retry_in for the RecordInvalid budget

The contract is real but scattered: an or return mid-line, a rescue at the bottom, a retry block elsewhere.

Both are correct. This is a readability argument, and I'll say so plainly — it's a style advantage, not a structural one. But "you can read the failure policy as a block of config" is worth something on a team where lots of people touch each other's jobs.

← →

Per-exception retry budgets, for free

This is the concrete one. retry_on takes a budget per error class. Native sidekiq_options retry: is a single global number — it caps every exception the same.

ActiveJob — one line per class

retry_on ActiveRecord::RecordInvalid, attempts: 3
# everything else keeps the default budget

Native — hand-rolled discrimination

sidekiq_options queue: :default # default budget (25)

sidekiq_retry_in do |retry_count, exception|
  :discard if exception.is_a?(ActiveRecord::RecordInvalid) &&
    retry_count >= RECORD_INVALID_MAX_ATTEMPTS - 1
end

The trap: writing retry: 3 to "match" attempts: 3 silently shrinks the default budget (25) down to 3 for transient infra errors — deadlocks, timeouts — giving up on recoverable work faster. The faithful native port is the block on the right.

This came straight out of the merge PR. The reviewer proposed retry: 3 as the port of retry_on attempts: 3. It looks equivalent and isn't — retry_on scopes the budget to one exception class; retry: 3 is global.

So the honest native equivalent is a sidekiq_retry_in block that branches on the exception. Which we have a pattern for — OpenAI::TransientRetryable, TriggerNowJob — but it's branching logic where ActiveJob is one declarative line. This is the cleanest example of the framework already solving something we re-solve by hand.

Arguments that survive a deploy

🔑

Keyword args

GlobalID lets you pass records and keywords. Adding or reordering an argument doesn't silently break jobs already in the queue mid-deploy, the way positional args can.

📦

Record loading

Records serialize to a GlobalID and reload on perform. A record deleted since enqueue raises RecordNotFound → handled by discard_on, declaratively.

🧭

Honest caveat

GlobalID is not "extra queries." It runs the same find your perform would — just earlier, in the deserialization layer. Same lookups, different place.

The deploy-safety point is the one the reviewer explicitly agreed was real. Positional args plus a signature change plus jobs in flight across a deploy is a genuine foot-gun.

The third card is me retracting one of my own earlier arguments. I'd claimed GlobalID adds two queries. It doesn't — it's the same find, just moved earlier. If I want this pitch to survive scrutiny I can't lean on a claim I already know is wrong.

← →

Less to write, less to learn

  • Less plumbing. No manual id passing, find_by guards, or rescue scaffolding — the framework does it.
  • Framework-standard. Any Rails developer already knows ApplicationJob, retry_on, perform_later. Less project-specific lore to onboard into.
  • Instrumentation. ActiveJob emits ActiveSupport::Notifications for enqueue / perform / retry / discard — a uniform hook for metrics and logs.
  • Discards stay observable. discard_on makes "give up" a named discard.active_job event — visible in APM and assertable in a test. The native find_by … or return / rescue equivalents just return: Sidekiq logs a processed job, and nothing — in prod or in a spec — tells a deliberate discard apart from a no-op run.
  • Portability. The queue backend is an adapter. If we ever evaluate alternatives, ActiveJob jobs move without rewrites. (Minor, but real.)

The onboarding point is underrated. New hires arrive knowing ActiveJob from every other Rails app. Native Sidekiq conventions — our middleware stack, our retry idioms — are local knowledge they have to absorb.

On the discard point, be precise: the win is the discard.active_job notification, not a magic test matcher. Our committed native spec and the original ActiveJob spec both assert give-up cases with not_to raise_error — so don't claim we "lost a matcher," that's checkable and false. The honest, unshootable claim is narrower: a native or return / rescue is observationally identical to a successful no-op, while discard_on fires an instrumented event you can subscribe to.

I'm flagging portability as minor on purpose. It's a real property but a weak argument on its own; I don't want to oversell it.

The honest part

Where native Sidekiq genuinely wins

  • Overhead. The adapter adds a wrapper and (de)serialization per job. Negligible for ordinary jobs; real at very high throughput and fan-out — exactly where you'd stay native.
  • Sidekiq-only features. Batches (we use Sidekiq::Batch in the candidate merger), Enterprise unique jobs, sidekiq_retry_in, fine-grained sidekiq_options — not first-class from an ActiveJob class.
  • Middleware interaction. Our server middleware is built around native jobs; ActiveJob wraps them in JobWrapper, which middleware has to special-case (our Current-class middleware already does). Tenant-on-retry through the adapter has bitten us before.
  • Retry layering. retry_on / discard_on sit on top of Sidekiq's own retry. Worth understanding how the two compose rather than assuming one cancels the other.
  • Testing seam. Flipping queue_adapter = :sidekiq in a test then needs jobs to run inline — but Sidekiq 8's Sidekiq::Testing.inline! do…end sets a thread-local mode that never reaches the Puma server thread (feature / Playwright specs). You have to reach past the public API to the global Sidekiq::Testing.__global_test_mode to make it cross the thread boundary. A native-only test wouldn't juggle two adapters at all.

I'm putting the cons on an accent slide so they read as a deliberate part of the argument, not fine print.

The throughput point is the platform team's strongest, and it's correct — Sidekiq is leaner per job. The feature-access point is concrete: a job that needs Batches simply can't be an ActiveJob. And I want to credit the middleware concern; it's real, even if it didn't apply to the specific job we were arguing about.

The testing-seam bullet is a fresh one — it bit our first Playwright spec that asserts on a job result. The shared sidekiq: true hook had only ever run in the example thread, so the block form's thread-local mode looked fine until a job ran in the Puma server thread and silently stayed queued. Honest cost of straddling two adapters; a native-only suite never sees it.

What I'm not claiming

So this doesn't get shot down on a point I never made.

  • Not "drop Sidekiq." It stays the engine — Enterprise, super_fetch, reliable scheduler, all of it.
  • Not "ActiveJob is faster." It isn't. There's measurable overhead. The operational read on that is correct.
  • Not "GlobalID saves queries." Same lookups, moved earlier. No saving, no extra cost.
  • Not a big-bang migration. Existing jobs stay; this is about the default for new ones.
  • And the platform team isn't "SRE" — it's a developer team with a wider remit. The operational lens is a strength here, not an opposing camp.

This slide is insurance. Every one of these is a claim someone could reasonably assume I'm making, and each one is either false or not mine. Clearing them up front means the discussion stays on the actual proposal.

The last bullet is a correction I owe the platform team — I framed their view as "SRE" in the thread and they rightly pushed back. Naming that here is just good faith.

Concretely

Default → ApplicationJob

  • Ordinary work: a record, some side effects, simple retry/discard rules.
  • The 80% case.

Reach for native Sidekiq when…

  • You need Batches, Enterprise unique, or custom sidekiq_options.
  • Very high throughput / fan-out where overhead matters.
  • You need direct middleware or retry-backoff control.

Make Current / tenant context adapter-agnostic so neither style can lose it. Write the default down. The consistency argument cuts both ways — it's only worth anything once we've picked one and documented it.

The "reach for native when" list is deliberately specific so the rule is decidable, not a vibe. If a job hits one of those, native is the right call and the proposal says so.

The tenant-context point matters regardless of which way we go — it's the actual root of the middleware concern, and fixing it de-risks both styles.

This is a team call

Consistency is an argument for picking one default going forward — we agree on that, we just disagree on which. That's decided here, in a Campfire topic or a Notion proposal, not inside one PR.

This is me agreeing with the reviewer's framing explicitly. The right venue for a convention is a team discussion. If we land on native Sidekiq, I'm aligned and the one job I converted is already there. If we land on ActiveJob-by-default, we've got a direction.
