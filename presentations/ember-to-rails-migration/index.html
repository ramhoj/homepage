Page by Page

Why we're moving off one big Ember app, and how we know each page still works.

The goal

One app, two engines under the hood

Most of what you use every day runs on a single big application called Ember, sitting in front of our Rails backend. We're moving it back to Rails — one page at a time, not all at once.

Old and new can exist side by side. A feature flag decides which one you see, and we can flip it back instantly.

Quick bit of context before the interesting part. Most of what you click through in the app today runs on one big application called Ember, sitting in front of our Rails backend. That's carried the product a long way, but keeping one huge single-page app and a growing Rails codebase in sync isn't free, and splitting focus across two frameworks forever isn't where we want to end up.

So we're gradually moving it back onto Rails, one page at a time. This is not a rewrite-everything-at-once gamble. Each page gets a life as Ember and a life as Rails, running side by side, and a feature flag decides which one you actually see. If the new version has a problem, we flip the flag and you're back on the old one instantly.

If you're in support or sales, this is also why some pages might start looking a little different over the next while — and why we can always switch straight back if something's wrong.

The hard part

Rebuilding a page is the easy part.

Knowing we got it right is the hard part. That's what this talk is really about.

Here's the part I actually want you to remember from this talk. Building the Rails version of a page isn't the hard part — our engineers do that well. The hard part is knowing, with real confidence, that we got it right.

A page can look completely finished and still be subtly wrong: a button missing for one kind of user, a permission that quietly stopped applying, a layout that only breaks for someone with a very long company name. Multiply that by hundreds of pages, and "we think it's fine" stops being good enough.

None of that shows up in a quick glance during a demo. It shows up months later, in a support ticket from the one customer it happened to.

The idea

Before we rebuild a page, we measure it

We record exactly what the current page says, how it's structured, and how it renders — a baseline of the truth. Only then do we build the Rails version. A machine compares the two and tells us precisely where they differ.

Think of it like a before-and-after photo — except a machine checks it for differences, not us.

So here's the idea that makes this whole approach work. Before we touch a page, we record a baseline of it exactly as it is today: what it says, how it's put together, how it actually renders on screen. Only then do we build the new Rails version. Once that's done, a machine — not a person — compares the two and tells us exactly where they differ.

It's not comparing code, it's comparing what a real visitor would actually see and use. Think of it like a before-and-after photo, except the machine is the one checking for differences, instead of someone squinting at two screenshots side by side. Nobody on the team has to spot the difference by eye, which is the part that doesn't scale.

That baseline becomes the yardstick for everything that follows, so nobody has to remember by heart what the old page used to do.

The process

The loop, end to end

Pick a page
→
Record it
→
Rebuild in Rails
→
Compare
→
Ship, flag off

It works the same whether a person does the migration or an AI agent does. Same checks, either way — which is what makes doing this across hundreds of pages realistic.

End to end, the loop looks like this. Pick a page. Record what it does today, exactly as it stands. Build the Rails version. Let the machine compare the two and report any differences. Then ship it behind a flag that's off by default, so we can turn it on gradually — a handful of people first — and turn it off instantly if anything looks wrong. The flag is what makes this safe; nobody is betting the app on one big cutover. Once we're confident, the flag moves from a handful of people to everyone, gradually, and we're watching closely the whole way.

And one more thing worth knowing: this works exactly the same whether a person does the migration or an AI agent does it. The checks don't care who did the work, and that consistency is what makes tackling this across hundreds of pages realistic instead of a fantasy.

Where we've landed

Work in progress — the honest version

So where are we, actually? I want to be upfront: this is genuinely a work in progress, not a victory lap.

← →

What's true today

One page migrated. The harness proven.

  • One real page — a settings page — has been migrated end to end, along with the shared navigation and sidebar around it.
  • The verification harness is real and working. It catches genuine differences, several we would not have spotted by hand.
  • The loop is the actual deliverable, not that one page.

Here's what's actually true today. One real page — a settings page — has been migrated end to end, along with the shared navigation and sidebar that wrap around it. The verification harness we just walked through isn't a slide, it's running: it catches real differences between the old and new versions, and it has already caught several that we would not have spotted by eye.

Here's the honest framing for all of it: the loop — measure, build, compare, ship — is the actual deliverable, not that one page. The first page was expensive, because it paid for all the scaffolding around it. The next ones should be much cheaper. That's the bet, and we haven't proven it at scale yet. We'd rather tell you that plainly now than oversell it and have to walk it back later.
