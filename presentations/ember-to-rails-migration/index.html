A deterministic harness for moving a page from Ember to Rails — and how we got there

This inovation week I was intressted in exploring what it would take to migrate an Ember SPA "page" to a Rails SSR page. I want to share some of the process and the harness I got after a week spent together with Claude. One page got ported, but that's the least intressting part.

← →

Rewriting is easier than verifying

I ran a similar experiment once before and it was a compleate whack-a-mole. While I got to 90% of a page port quite quickly, the last 10% was a mess, and it come down to verifibility.

Ember is the specification, and sameness is measured rather than reviewed.

The reason for the "even where Rails is better" rule: a migration that also improves things is a migration whose failures cannot be localised. When something looks wrong, you want exactly one explanation available — "the port is wrong" — not two.

Improvements happen. They happen deliberately, afterwards, as their own change, with a record of what was found. Every accessibility finding we hit got written into the manifest rather than fixed on the spot.

Chapter 1 — How it started

We wrote a plan, without perfecting it

Turns out, comparing real application pages isn't trivial. In a day we got to a plausible plan but at over 8,000 lines I refused reviwing any more iterations. The best decision this week came from being lazy.

8,197lines of plan 5,035lines of harness it planned

Building the wrong thing can be expsneive but so can planing the thing that can't be built. I moved on to proving a imperfect plan.

Worth being honest about the ratio. Some of it is defensible — most of that prose is why, which code can't carry, and it's the reason a second person can pick this up. But it was still too much, and we only found that out by building.

The plan was about comparing. The work was about preconditions.

What the plan was

Five comparison algorithms

Diff the trees. Diff the styles. Diff the pixels. Nothing in it said what makes a comparison mean anything.

What it cost

Seven preconditions

Every one learned by being violated first: right implementation, declared data, a stable environment, a baseline that isn't quietly describing something else.

The comparators turned out to be the easy part, for a reason visible in advance if anyone had looked: we did not write them.

Of the first 33 decisions, five were about how to compare. Fourteen were about whether the thing measured is the thing meant.

The sharpest example is the pixel noise floor. An earlier spike concluded that ~3% differing pixels is simply the inherent noise of comparing two implementations, and that no threshold and no pixelmatch option moved it. Those measurements were careful and the conclusion followed from them.

It was still wrong. It was the noise floor of that capture design — two browser contexts, photographed separately. Photograph both implementations from the same context in the same session and the measured floor is zero. Two months of tuning the comparator, and the problem was in the precondition.

What it's made of

Six stages, and the split that matters

bin/ssr/verify all settings-overview   # every stage, stopping at the first failure

Gates fail the build. Instruments report and a human decides. A check that produces judgement calls is a check that will eventually be tuned until it passes — and a gate that gets tuned is worse than no gate.

The order isn't arbitrary: an early failure usually explains everything below it, so the stack stops at the first red rather than handing you four reports of one cause.

Note the cost column. The two cheapest gates are, as it turns out, the two that catch almost everything. We'll get to how we know that.

← →

The accessibility tree as the diffable artefact

You can't diff two DOMs — the Rails markup is deliberately allowed to differ. But the browser will hand you what the page means, and that is text, and text diffs.

spec/baselines/aria/settings-overview.yml — captured from Ember, before any Rails existed 
- heading "Settings guide" [level=1]
- button "Set up departments and roles":
  - checkbox "Set up departments and roles"
  - text: Set up departments and roles
- paragraph:
  - text: Working with departments is a great way to organize your entire Teamtailor account…
  - link "Configure departments and roles →":
    - /url: /companies/golden/settings/organization/departments

That last line is the whole argument for this gate. Point the link somewhere else and its text is identical, its role is identical, and every pixel of it is identical. Nothing else in the stack looks at an attribute with no appearance.

This is the one gate that cannot be dropped. When we mutation-tested — coming up — there was exactly one planted bug that a single gate caught alone, and it was this: a changed href.

It's also where most first attempts fail, and almost always for the same reason: an icon-only control with no accessible name. That's a real finding, not a nuisance. If the tree can't name it, no assistive technology can either.

A failure has to name the fix

  in button "Set up departments and roles"
    - button "Set up departments and roles"
    + button
      ↳ no accessible name in Rails -- an icon-only control needs an
        aria-label, or text only a screen reader reads

- gone, + arrived, ~ the same node said differently about. Grouped by the region it's in, so a reordered item reads as itself rather than as an anonymous box.

The layout gate does the same job for appearance, and adds one rule: report the outermost divergence and stop. One wrong container moves everything inside it, and a list of forty consequences is a worse report than the one cause.

This is the part that actually saves the hours. An agent — or a person — reading "no accessible name in Rails, an icon-only control needs an aria-label" goes and fixes it. Reading "trees differ" goes and stares at two thousand lines of YAML.

Matching elements across the two implementations is its own problem, because we deliberately don't require the same markup. The layout gate matches by identity — role, accessible name, text — at several strengths, and reports how many it could only match by appearance rather than identity. That number is a warning sign on its own.

← →

One page, migrated

Server-rendered Rails, behind a Flipper flag. The same URL still answers with Ember for everyone else — an impl query parameter lets staff open both side by side.

One URL, two implementations, a server-side decision. That's what makes any of the comparison possible: the harness points the same browser at the same address twice.

Every rendered document carries an implementation stamp, and every verifier asserts it on arrival. That's not a debugging convenience — it prevents the failure that silently invalidates everything, which is a flag that didn't take effect and Ember being compared against itself.

36 pixels out of 2,077,744

Magnified 14×. One letter, one sub-pixel of antialiasing, in “Configure departments and roles”.

Two million pixels. Thirty-six of them differ, and they're all in one glyph. Left and right on this slide are the actual crops — I genuinely cannot tell them apart, and neither can anyone else.

This is exactly why the photo is an instrument and not a gate. If this failed the build, the only rational response would be to add a threshold, and once there's a threshold there's a number someone tunes.

← →

Its job is attribution, not detection

The instrument clusters differing pixels into regions and draws a ring round each one, on the page itself. One ring, round one letter.

The output isn't a number, it's a picture of where to look. That's the difference between "0.002% of pixels differ" — which tells you nothing — and "here, this word".

It also names its own contaminants. A flash message that appeared on one side and not the other used to read as a real divergence; now the instrument says so.

The one that scared us

The camera never saw half the page

ember 1136x1829, rails 1136x1829: identical

The same SHA256 — not merely below a threshold. Except it compared the top 900 pixels and called the other 929 identical: Playwright returns an image the full height of an element taller than the viewport and paints only the part that was inside it. The blank remainder was blank on both sides, so it subtracted to nothing. That green had already been quoted as evidence the migration was pixel-perfect.

A false green over unexamined input is the most expensive defect a harness can have.

Half the page. Reporting identical. With a matching hash, which is the most convincing possible way to be wrong.

And note how we found it — not by reading the code, not by review. We found it by planting a bug in the bottom half of the page and watching this thing stay green.

So we broke it nine ways on purpose

One regression at a time in the migrated Rails, every gate run alone against each — because a stack that stops at the first failure can't tell you which of the later gates would also have caught it.

It found three defects in the harness in one afternoon: the fold bug, the conformance mode counting other gates' examples as its own verdict, and a number the layout gate had always computed and never printed.

And it settled what each gate is actually for. Row 8 is the argument for the aria gate — one gate, alone. Rows 4 and 5 are the argument for layout: among gates it's the only one that sees appearance at all.

The uncomfortable row is conformance: it caught nothing aria didn't, at five times the wall clock. But that's a fact about the mutation set, not the gate — not one of these nine changed what a control does when you press it. The honest conclusion is that this set under-samples behaviour.

Nobody had asked the second question

Gates were argued for, individually and in advance, on what each could catch. Nobody had asked what each did catch that the others missed.

The answer was not the one the arguments predicted. The gate written first and trusted most was the least differentiating; the instrument nobody gated on was quietly returning false greens. Both facts cost one afternoon to establish, and neither was visible from reading the code.

Mutation-test the gates before the second page, not after the tenth.

I think this generalises well past this project. Any time you build something whose job is to catch problems — a linter, a test suite, a review checklist — you can only argue about what it could catch until you deliberately introduce the problems and watch.

Chapter 3

Not doing this fifty times

Primitives, surfaces, pages

← →

Three things get migrated, on three schedules

  • Primitives — buttons, badges, dropdowns. View-only, no domain logic, every class string from one source per primitive so the same button can't be re-derived on fifty pages. Parity-tested against the Ember original for every variant the application actually uses.
  • Surfaces — shared chrome. The global banner and a section's sidebar. Peers of pages rather than a special case: a manifest, baselines, gates — just no URL and no flag. Each page's baseline excludes the surfaces it renders, so a surface is measured in one place instead of in every page that shows it.
  • Pages — a manifest, a conformance spec pinned green against Ember, two baselines, a controller and a template.

Each shared thing is migrated once, on demand, by the first page that needs it — never speculatively. The first page into a section pays for both levels of chrome. That cost is real, front-loaded, and paid once.

This is the answer to "you migrated one page, so what". Page one of Settings cost the global banner, the settings sidebar, and seven primitives. Page two costs a manifest, a spec and a template — everything underneath it is already there and already proven.

The "every variant the application actually uses" bit isn't a promise, it's asserted. There's a demand map that reports which primitive variants the app uses and where, and the parity spec has to cover them.

← →

Things we built and then unbuilt

  • A namespace that described its own history. Everything migrated lived under Migrated:: — which is a statement about how the code got here, and stops being true the day Ember is deleted. About 90 files renamed. Then we made the same mistake one layer up, and renamed again.
  • A mode called visual that never rendered a pixel. It read the CSSOM. It sat directly next to one called pixels. Nobody could remember which was which, including the people who named them.
  • A stamp that stamped everything. The implementation stamp got applied to every unmigrated page in the app, cheerfully labelling the entire product as part of a migration that had touched one page.
  • A 129-file freeze. The idea was to stop anyone editing Ember out from under a migrated page. The set was so wide it would have blocked the team from hotfixing pages nobody had migrated. Now it freezes only what a migrated route actually reaches.

I want to be honest that none of these were found by thinking harder. Every one was found by using the thing.

The namespace one is my favourite, because we got the principle right — the Rails shouldn't have to be changed once the migration is done, so it must not know it was migrated — and then still applied it at only one of the two layers it applied to.

What it cannot see

A fixture can only make visible a difference that the data determines.

Pages are measured against a golden tenant planted through the app's own paths. Anything that tenant can't produce — an unread badge that needs real activity behind it — is a branch no gate ever visits.

  • Baselines are machine-bound. The platform shapes the text and the product branches on it, so the gates refuse rather than compare: “This baseline was captured on linux, and this is darwin.”
  • The gates prove sameness, not quality. Nothing here has an opinion about whether the Rails is any good. That's still review.
  • The mutation set under-samples behaviour. Every planted bug damaged rendering. The next page should plant one that changes what a control does.

A harness that doesn't say what it can't see is worse than no harness, because people trust it. So this is written down as prominently as the capabilities are.

The refusal message is deliberate too. It doesn't fail with a diff of two machines — it declines to compare, and tells you to re-capture in the container.
